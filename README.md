# InspoFlow-Coze-Agent

> **灵感不设防，创作不断流。** 一个面向 LOFTER 创作者的「灵感捕获 → 结构化沉淀 → 内容转化」AI Agent 工作流产品。

## 1. 🎯 项目背景：基于 LOFTER 创作者身份发现的痛点

### 1.1 用户是谁

LOFTER 是国内活跃的图文 / 同人创作社区，聚集了大量**非专业但高活跃**的内容创作者。他们不同于职业自媒体，创作动机以兴趣、热爱和圈层认同为主，创作频率不稳定但粘性极高。

### 1.2 洞察过程（身份代入式调研）

在设计产品前，我们以「LOFTER 创作者」的身份真实使用平台，通过沉浸式体验 + 用户访谈，梳理出创作全流程中的关键断点：

```
浏览社区 / 阅读作品 / 生活碎片
        │
        ▼
   ⚡ 灵光一现（灵感产生）
        │
        ▼
   📝 随手记录（通常散落在备忘录、相册、聊天记录）
        │
        ▼
   💤 灵感沉睡（记录完就忘，再无下文）
        │
        ▼
   ✍️ 正式创作（想用却找不到、记不清当时的想法）
        │
        ▼
   😞 灵感丢失 / 情绪断层
```

### 1.3 核心痛点（P0-P3 优先级排序）

| 优先级 | 痛点 | 用户原话 / 行为证据 | 影响 |
| --- | --- | --- | --- |
| P0 | **灵感碎片化、无沉淀** | "当时觉得超有感觉，现在翻手机死活找不到那条记录" | 创作素材大量流失，灵感复用率低 |
| P0 | **记录与创作断层** | 记录时只存了碎片，创作时需要重新回忆、补全上下文 | 创作启动成本高，常因此放弃 |
| P1 | **缺乏结构化整理** | 灵感散落在多个 App，无分类、无标签、无关联 | 检索困难，无法形成素材库 |
| P1 | **情绪与灵感捆绑丢失** | 灵感往往伴随强烈情绪，但纯文字记录丢失了当时的情绪语境 | 转化时缺乏情感浓度，作品感染力下降 |
| P2 | **缺少"转化抓手"** | 即使有灵感，也不知道如何把它扩展成完整作品 | 停留在"记了但没产出" |

### 1.4 机会点

> 创作者的瓶颈往往不是"没有灵感"，而是**"灵感没有被系统化地捕获、组织与转化"**。

InspoFlow 通过 AI Agent 工作流，把「灵感产生 → 灵感识别 → 素材沉淀 → 内容转化」这条链路自动化、产品化，让每一次灵光一现都能被**及时捕获、结构化留存、随时可复用**。

## 2. 🏗️ 产品方案：Agent 多节点工作流架构

### 2.1 设计原则

- **低摩擦捕获**：用户记录灵感的行为成本趋近于零（一句话 / 一段语音 / 一张图即可触发）
- **全链路自动化**：从灵感输入到卡片生成，由 Agent 工作流自动完成，无需用户手动整理
- **结构化沉淀**：每一次灵感都以结构化数据落库，形成可检索、可关联、可持续生长的灵感资产
- **可视化交付**：最终以「灵感卡片」形式呈现，兼顾可读性与分享性

### 2.2 工作流总览（01 → 06 多节点架构）

```
 ┌─────────────────────────────────────────────────────────────────┐
 │                    InspoFlow Agent 工作流                        │
 │                                                                 │
 │  [01 灵感识别] → [02 意图解析] → [03 结构化抽取] → [04 数据入库]  │
 │       │              │              │              │            │
 │       ▼              ▼              ▼              ▼            │
 │  [05 关联补全] ───────────────────────────────→ [06 灵感卡片生成]  │
 │                                                                 │
 └─────────────────────────────────────────────────────────────────┘
```

### 2.3 节点详解

| 节点 | 名称 | 核心职责 | 关键输入 → 输出 | 设计要点 |
| --- | --- | --- | --- | --- |
| 01 | **灵感识别** | 识别用户输入是否为「创作灵感」，过滤闲聊与无效输入 | 用户原始输入 → `is_inspiration` 判定 + 灵感类型标签 | 引入阈值判断，避免每条消息都触发全流程，控制成本 |
| 02 | **意图解析** | 解析灵感的创作意图与潜在方向 | 灵感文本 → 创作类型（同人/原创/随笔/脑洞）、目标受众、创作动机 | 为后续节点提供结构化上下文 |
| 03 | **结构化抽取** | 从自由文本中抽取实体、场景、情绪、人物、世界观等要素 | 灵感文本 → `inspiration_entity` JSON 结构 | **核心节点**：输出必须严格 JSON 化，供下游直接消费 |
| 04 | **数据入库** | 将结构化灵感写入数据库 | JSON → 数据库 `inspirations` 表记录 | 唯一 ID 生成、幂等写入、脏数据清洗 |
| 05 | **关联补全** | 检索历史灵感，建立关联，补充缺失上下文 | 当前灵感 + 历史记录 → 关联关系 + 上下文增强 | 让灵感库具备"生长性" |
| 06 | **灵感卡片生成** | 将灵感封装为可视化卡片并交付用户 | 结构化数据 → 卡片内容 + 封面 + 标签 | 面向用户的核心交付物，兼顾美观与信息密度 |

### 2.4 产品价值（面试要点：为什么是 Agent 工作流而不是单次 Prompt）

| 维度 | 单次 Prompt（LLM 直出） | 多节点 Agent 工作流（InspoFlow） |
| --- | --- | --- |
| 可靠性 | 输出结构不稳定，依赖运气 | 每节点职责单一，可独立调试、可观测 |
| 可扩展 | 加需求 = 重写 Prompt | 加需求 = 插入新节点，模块化复用 |
| 成本控制 | 每次全量调用大模型 | 01 节点前置过滤，无效输入不触发后续 |
| 数据资产 | 结果不落库、不可复用 | 每步结构化入库，形成可持续积累的素材库 |
| 可维护 | 黑盒，出错难定位 | 节点级 trace，问题精准定位 |

## 3. 🔄 数据流设计

### 3.1 完整链路

```
 ┌──────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
 │  UI 事件  │ →  │  调用工作流    │ →  │  数据库读写    │ →  │ 全局变量传参   │
 │ (用户输入) │    │ (Agent 编排)  │    │ (结构化持久化) │    │ (跨页/跨节点)  │
 └──────────┘    └──────────────┘    └──────────────┘    └──────────────┘
      │                 │                   │                    │
   触发入口           业务编排             数据落盘            上下文共享
```

### 3.2 分阶段数据流

#### 阶段 A：UI 事件触发

- **事件源**：用户在 Agent 聊天页 / 卡片页输入灵感（文本、图片、语音多模态）
- **触发策略**：
  - 显式触发：用户明确说"记录灵感 / 帮我生成灵感卡片"
  - 隐式触发：01 灵感识别节点判定命中后自动触发
- **输入载荷**：`{ raw_input, user_id, source, timestamp, media_type? }`

#### 阶段 B：调用工作流（Agent 编排）

- 工作流通过 **Start 节点** 接收 UI 事件参数，按 01→06 顺序执行
- 节点间通过 `{{node_id.field}}` 引用上游输出，形成数据依赖链
- 每个 LLM 节点输出经**代码节点清洗**后再进入下一节点，保证数据质量

#### 阶段 C：数据库读写

| 操作 | 节点 | 说明 |
| --- | --- | --- |
| 写入 | 04 数据入库 | 结构化灵感落库，字段与 03 节点 JSON 对齐 |
| 查询 | 05 关联补全 | 按用户 + 标签/实体检索历史灵感，建立关联 |
| 更新 | 04/05 | 关联关系回写，丰富灵感上下文 |
| 读取 | 06 卡片生成 | 读取完整记录，生成卡片 |

**表结构设计（核心表 `inspirations`）**：

```sql
inspirations (
  id            TEXT PRIMARY KEY,      -- 灵感唯一 ID
  user_id       TEXT NOT NULL,         -- 创作者 ID
  raw_input     TEXT,                  -- 原始输入（保留原文，防信息丢失）
  entity_json   JSONB,                 -- 结构化抽取结果（实体/场景/情绪等）
  inspiration_type TEXT,               -- 创作类型（同人/原创/随笔/脑洞）
  emotion       TEXT,                  -- 情绪标签（保留情绪语境）
  tags          TEXT[],                -- 标签数组（用于检索关联）
  related_ids   TEXT[],                -- 关联灵感 ID
  status        TEXT DEFAULT 'active', -- 状态（active/archived/used）
  created_at    TIMESTAMP DEFAULT now()
)
```

#### 阶段 D：全局变量跨页传参

- **全局变量（Global Variables）** 用于跨页面 / 跨节点共享上下文，如：
  - `user_id`：贯穿全流程的身份标识
  - `current_inspiration_id`：当前处理的灵感 ID，供多页面读写同一记录
  - `workflow_context`：累计的结构化上下文，避免重复抽取
- **设计原则**：
  - 全局变量只存**跨页必需的上下文**，单节点内部数据不占全局
  - 写入时机集中在节点边界，避免并发写冲突
  - 读取时做空值兜底，防止变量未初始化导致链路中断

### 3.3 数据流设计要点（面试亮点）

1. **原文优先**：无论怎么结构化，始终保留 `raw_input` 原文，结构化只是索引而非替代——保证信息不丢失
2. **节点边界清洗**：每个 LLM 输出在节点出口做格式校验 + 清洗，坏数据不进库
3. **链路可观测**：节点级 trace 记录输入输出，异常可回溯到具体节点
4. **幂等写入**：同一灵感重复触发不产生脏数据

## 4. 🧗 核心踩坑经验（实战复盘）

### 4.1 LLM 输出 JSON 格式漂移

**现象**：03 结构化抽取节点要求 LLM 输出 JSON，但实际输出频繁出现：

- 键名漂移：`entity_json` 变成 `entityJson` / `Entity`
- 多余包裹：输出被 Markdown 代码块 ```json ``` 包裹
- 注释残留：JSON 中夹杂 `// 注释`
- 结构缺失：数组字段偶发缺项 / 类型错误

**根因**：LLM 生成是概率性的，Prompt 约束无法 100% 保证格式合规；下游节点直接消费原始输出必然被"脏数据"击穿。

**解决方案**：

```
① Prompt 层约束
   - 明确输出 Schema（字段名 + 类型 + 必填性）
   - 给出"正例 + 反例"，Few-shot 引导
   - 声明"只输出 JSON，禁止任何解释、代码块标记"

② 输出解析层兜底（代码节点）
   - 剥离 Markdown 代码块包裹（```json ... ```）
   - 键名归一化映射（entityJson → entity_json）
   - JSON.parse 失败时进入修复分支：提取最外层 {} 重试

③ 数据校验层拦截
   - 校验必填字段、字段类型，非法数据标记为 failed 不进库
   - 失败记录留痕，用于持续优化 Prompt
```

**效果**：JSON 解析成功率从 ~70% 提升到 98%+，坏数据不再击穿下游节点。

### 4.2 变量作用域问题

**现象**：

- 节点 A 定义的变量，在节点 B 引用时取到空值
- 工作流重跑时，上一次的变量值残留污染本次结果
- 全局变量在多页面并发访问时出现"你改我读"的脏读

**根因**：

- 混淆了「节点局部输出」与「全局变量」的作用域边界
- 依赖隐式作用域，未显式声明变量生命周期
- 全局变量读写未做时序控制

**解决方案**：

```
① 明确作用域三层模型
   - 节点局部：仅当前节点内部使用，节点结束即销毁
   - 工作流级：通过 {{node.field}} 引用，仅存在于本次工作流运行
   - 全局级：跨页面/跨运行持久共享，只在节点边界写入

② 写入时机收敛
   - 全局变量只在关键节点出口赋值（如 03→04 边界）
   - 避免在循环 / 条件分支中随意写全局，防止竞态

③ 空值兜底
   - 引用全局变量前先做空值判断，为空时走默认分支
   - 关键路径变量初始化失败时直接 fail-fast，不带着脏状态继续

④ 命名规范
   - 全局变量统一 `g_` 前缀，节点变量统一 `node_` 前缀，从命名上隔离作用域
```

### 4.3 脏数据清洗

**现象**：数据库中积累了大量脏数据：

- 重复记录：同一灵感被多次触发写入
- 空壳记录：raw_input 为空 / 只有默认值的半成品
- 格式漂移：早期版本字段结构与新版本不一致
- 无效关联：related_ids 指向已删除的灵感

**根因**：数据写入入口不设防、Schema 演进未做迁移、清理无定时机制。

**解决方案**：

```
① 入口防脏（事前）
   - 写入前校验：raw_input 非空、必填字段齐全、JSON 结构合法
   - 幂等键：以 user_id + 内容哈希 生成唯一键，重复触发走更新而非新增

② 定期清洗（事中）
   - 定时任务扫描：剔除空壳记录、合并重复记录
   - 孤立关联修复：清理指向不存在 ID 的 related_ids

③ Schema 兼容（事后）
   - 版本号字段：记录写入时的 schema_version
   - 读取侧兼容：低版本数据按默认值补齐，不因字段缺失直接报错
   - 提供一次性迁移脚本：旧数据批量升级到新结构
```

### 4.4 其他值得记录的坑

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **Prompt 注入** | 用户输入包含恶意指令，被 LLM 当成系统指令执行 | 用户输入与系统指令隔离，用户内容只作为数据处理对象，不做指令拼接 |
| **长文本截断** | 灵感过长时 LLM 输出被截断，JSON 不完整 | 输入截断策略 + 解析失败重试（缩小输入窗口） |
| **情绪语境丢失** | 结构化后情绪标签过于抽象，转化时感受不到"当时的情绪" | 保留原始文本片段作为"情绪锚点"，卡片中呈现原句 |
| **节点级联失败** | 上游节点失败导致整条链路中断，且难定位 | 节点级 try-catch + trace 日志，失败节点可单独重跑 |
